# 15-thn_project — PILOT Studio 1.0

이 GitHub 저장소에는 최종 프로그램의 **소스·설계 문서·시험 코드·빌드 설정**을 보관합니다. 개발 환경과 별도 런타임 준비는 [저장소 준비 안내](docs/REPOSITORY_SETUP.md), 구현 기준은 [최종통합 설계서](docs/PILOT_인터페이스_최종통합본_ASAP반영.md)를 참조하세요. 아래 `dist` 경로의 EXE/설치파일은 로컬 배포 산출물이며 Git 소스에는 포함하지 않습니다.

PILOT 인터페이스 최종 통합설계 v1.6과 ASAP 구현설계 v0.4를 기준으로 만든 Windows용 통합 프로그램입니다. 프로젝트·CAD 대응·공정/공구·순서 편집·검증·영상 출력·이력/학습을 하나의 독립 프로그램 창에서 사용합니다.

## 실행과 설치

배포용 설치파일은 `dist/PILOT-Studio-Setup-1.0.0.exe`입니다. 설치하면 필요한 런타임과 바로가기가 등록됩니다. `PILOT Studio` 바로가기 또는 설치된 `PILOT-Studio.exe`로 실행합니다. 기본 브라우저나 CMD를 실행하는 방식은 제공하지 않습니다.

설치 전 바로 실행하려면 `dist/PILOT-Studio/PILOT-Studio.exe`를 더블클릭합니다. 실행파일과 `_internal`을 포함한 `PILOT-Studio` 폴더 전체를 유지해야 합니다. 단일 설치파일은 약 1.2GB이며 포함된 프로그램 구성 요소는 약 3.7GB입니다.

프로그램 파일과 사용자 자료를 분리합니다. 기본 프로젝트·DB·CAD·ASAP 결과·영상·백업은 `%LOCALAPPDATA%/PILOT Studio/data`에 저장합니다. 앱 전용 MariaDB는 루프백 주소에서 별도 프로세스로 동작하며 기존 MariaDB 서비스/DB를 사용하거나 변경하지 않습니다. DB 인증 설정은 Windows DPAPI로 보호합니다.

설치형 패키지는 Python/Node/CATIA 설치에 의존하지 않으며 CAD 런타임·별도 ASAP Python/네이티브 엔진/가중치·영상 렌더용 Chromium/FFmpeg·MariaDB를 포함합니다. 독립 창은 WebView2를 사용하며 설치 프로그램에서 구성 요소를 준비합니다. 확인한 환경과 별도 PC 인수 상태는 `docs/IMPLEMENTATION_STATUS.md`에 기록합니다.

## 사용 순서

1. 프로젝트에서 제품 정보를 입력합니다. 모델 화면에서 `완제품만` 또는 `완제품＋하위 부품`을 선택합니다.
2. 완제품 STEP을 등록합니다. 하위 부품 방식은 기준 STEP을 여러 개 추가하고 파일 상태·형상 범위·매칭 후보의 3D 정합을 검토합니다. 반복 볼트는 위치별로 다른 배치 ID를 유지합니다.
3. 단위 묶기/해제·구성원 이동/분할·수동 대응으로 실제 함께 투입할 단위를 정합니다. 원본 구성원·솔리드의 누락/중복 없이 전체 단위를 확정합니다.
4. 자동 전처리·ASAP 실행으로 OBJ·원본 솔리드 충돌 입력·격자 계약·단위별 네이티브 사전시험·실제 탐색을 수행합니다. 준비 성공, 전체 순서 성공, 실제 경로 성공은 각각 표시됩니다.
5. 완료된 실제 ASAP 결과를 `공정 초안`으로 가져옵니다. 원시 실행은 보존됩니다. 품번·명칭·체결/검사·공구/소켓·토크·주의사항·현장 규칙을 검토합니다.
6. 순서를 이동할 때 목표 위치와 선행 규칙을 확인하고 변경 사유를 기록합니다. 설치 순서·대상·경로 조건이 바뀌면 실제 ASAP 경로가 낡은 상태로 표시됩니다. 새로운 경로 검증 전 임의 직선 애니메이션으로 대체하지 않습니다.
7. 전체 검증 후 검토자가 계획을 확정합니다. 불변 확정본으로 미리보기·MP4·Web ZIP을 만들고 저장소 화면에서 백업할 수 있습니다. 초안 출력은 DRAFT로 구분됩니다.

완제품만 있어도 단위를 구성할 수 있습니다. 하위 부품은 완제품을 대체하거나 추가 설치하는 형상이 아니라 단위 식별의 기준입니다. 일부 기준 파일만 있는 경우 매칭한 단위와 잔여 수동 단위를 함께 사용할 수 있습니다. 이름/접촉만으로 모든 항목을 자동 병합하지 않습니다.

## 검토와 계산 범위

ASAP `learn`은 사전학습 가중치의 추론이며 GNN 신규 학습이 아닙니다. `heur-out` 비교와 자체 규칙/기하 생성기·별도 로컬 선호 학습은 각각 다른 결과로 저장됩니다. Assembly Flow·예제 순서·품명 기반 고정 정답을 자동 생성의 우선순위로 사용하지 않습니다.

물리 입력은 강체 근사입니다. 경고 허용 테스트는 초기 침투·OCCT 경고를 숨기지 않으며 실제 이동의 충돌/지지 검사를 유지합니다. 유연체 변형·실제 공구 이동·로봇 동작은 별도 현장 검토가 필요합니다. 입력한 원통 공구 외형/접촉점이 있는 경우 정밀 BREP의 해당 자세를 검사합니다. 자료가 부족하면 미검토로 남깁니다. 범위 한정 유연체 공정 검토 기록은 변형 시뮬레이션 완료가 아니며 실제 충돌/계산 실패를 면제하지 않습니다.

프로그램은 모든 STEP의 계산 또는 모든 제품의 전체 순서 성공을 보장하지 않습니다. 실패 단계·해당 배치/쌍·수치·원문·로그·종료 원인을 확인할 수 있습니다. 현재 실제 HVJB 전체 전처리 성공은 확인했지만 전체 순서 성공은 확보하지 못했습니다. 작은 A/B 검증 형상의 성공을 HVJB/PRA 현장 인수로 간주하지 않습니다.

## 저장·복구

DB는 MariaDB이며 SQLite 운영 대체를 사용하지 않습니다. 백업 ZIP은 일관된 논리 DB 스냅샷과 해시 manifest·관리 파일·ASAP 입력/경로·불변 확정본·영상·모델을 포함합니다. 실행 중인 작업이 있으면 백업/복원을 차단합니다. 복원은 새 독립 DATA/DB로 수행하고 원래 저장소를 덮어쓰지 않습니다. 반환된 새 저장소로 시작해 자료를 확인할 수 있습니다.

앱 종료나 취소는 작업자의 종료를 확인하고 결과를 중단/취소 상태로 보존합니다. 같은 저장소의 중복 실행은 차단합니다. 진단은 사용자 데이터의 logs와 해당 job/run 폴더에 저장됩니다. 원본·DB·실행 캐시를 임의로 삭제하지 마세요.

## 개발 구조

- `backend`: 프로젝트·계획·도메인 검증·공구·MariaDB·불변 스냅샷·명령 멱등성·영상·백업 API.
- `asap_service`: 검증된 CAD/매칭/단위/전처리/실제 ASAP 어댑터. UI는 `/api/asap`에 연결합니다.
- `frontend`: 7개 화면과 ASAP 작업 화면, ID 기반 3D 선택, 실제 행렬 경로·전체 자세·타임라인·미리보기.
- `desktop`: WebView2 독립 창과 앱/DB 수명 관리.
- `packaging`: 실행파일·런타임·설치파일 빌드 정의.
- `tests`, `evidence`: 검사와 개발 증적. 사용자 기본 프로젝트에 시험 자료를 자동 등록하지 않습니다.

검증 결과와 구현 범위는 `docs/IMPLEMENTATION_STATUS.md`, 구현 기준은 `docs/SPEC.md`와 `docs/ASAP_SPEC.md`를 참조하세요.
